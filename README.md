# Траты Сани

Настольное приложение для Windows (Electron + React + SQLite) для учёта расходов, внесений, остатка денег и формирования отчётов за период.

Валюта: **тенге (₸, KZT)**.

## Установка на другой компьютер

Готовый установщик: **`release\Траты Сани Setup 1.0.0.exe`**

Установщик уже содержит подготовленную базу данных с категориями — при первом запуске на новом компьютере она автоматически разворачивается в `%APPDATA%\Траты Сани\database\expenses.db`. Устанавливать Node.js на целевой компьютер **не нужно**.

## macOS (Apple Silicon)

Готовый `.dmg` собирается в облаке GitHub Actions — Mac не нужен:

1. Загрузить репозиторий на GitHub
2. Открыть **Actions → Build macOS (arm64) → Run workflow**
3. Скачать артефакт `Traty-Sani-mac-arm64` (файл `.dmg`)

Если есть свой Mac — то же самое выполняется локально:

```bash
npm run build:mac      # electron-builder --mac --arm64
```

Результат: `release\Траты Сани 1.0.0 arm64.dmg`

**Подпись macOS-версии**

Образ подписывается **ad-hoc** (`codesign --force --deep --sign -`) на CI-раннере, до создания `.dmg`. Это обязательно:

- electron-builder с `identity: null` подпись пропускает, и остаётся только подпись линкера — бандл с незапечатанными ресурсами и несвязанным `Info.plist` macOS считает повреждённым и не запускает
- Порядок важен: если поручить сборку образа electron-builder'у после подписи, он перезапишет бандл, и подпись пропадёт. Поэтому `.dmg` собирается вручную через `hdiutil` из уже подписанного `.app`

Проверка `codesign --verify --deep --strict` выполняется на CI и валит сборку, если подпись неполная.

**Ограничения macOS-версии**

- Собирать `.dmg` можно **только на macOS** — electron-builder использует системные утилиты macOS для создания образа. С Windows это не работает, поэтому Windows-сборка и macOS-сборка выполняются разными командами
- Подпись ad-hoc не заменяет подпись разработчика: при первом запуске macOS может показать предупреждение. Открыть: правый клик по `.app` → «Открыть» → «Открыть». Либо «Системные настройки → Конфиденциальность и безопасность» → «Открыть всё равно»
- Подпись и нотаризация (чтобы предупреждения не было вовсе) требуют Apple Developer Account и платного использования GitHub Actions
- **Автообновление отключено**: обновления ставятся вручную, образ берётся из артефактов Actions. Причина описана в разделе «Обновление программы»
- Требуется macOS 11.0 или новее (в CI собирается под macOS 14)
- Собран только под Apple Silicon (M1/M2/M3/M4). Для Intel добавьте `--x64` в `build:mac` и `x64` в `mac.target`

**Платформенные различия в оформлении окна**

На macOS системные кнопки окна находятся слева, а не справа, поэтому используется `titleBarStyle: 'hiddenInset'` с индивидуальным положением кнопок, а заголовок сдвинут вправо. Логика приложения, база и отчёты на обеих платформах идентичны.

## Возможности

**Резервные копии**
- Кнопка «Резервная копия» в боковой панели создаёт копию БД с меткой времени
- Автоматическая копия создаётся при каждом запуске **перед** изменением схемы — это точка отквата для миграций
- Хранятся последние 10 копий, старые удаляются
- Папка: `%APPDATA%\Траты Сани\backups` (Windows) и `~/Library/Application Support/Траты Сани/backups` (macOS)

**Категории и подкатегории**
- **Уровень 1 — категория.** Встроенные: «Закуп», «Такси». Свои добавляются через «Управление категориями»
- **Уровень 2 — подкатегория.** У «Закуп» по умолчанию: Российский, Рыба, Боксы, Курица, Овощи, Хоз.товары, Кола, Вода, Камшат
- **Уровень 3 — статья.** Создаётся внутри любой подкатегории («Статья для "Рыба"…»). Используется в форме траты и в разбивке отчёта
- Встроенные категории и подкатегории можно удалить — удалённое не возвращается при следующем запуске (помечается в таблице `settings`)
- Перед удалением показывается, сколько статей, подкатегорий и трат будет затронуто
- Клик по подкатегории или статье в списке категории сразу подставляет её в форму траты

**Панель категорий (плитки)**
- Категории выведены **плитками**, как на телефоне: значок сверху, **название под плиткой**. У плитки с подкатегориями есть уголок со счётчиком
- Нажатие на плитку раскрывает **список подкатегорий и статей** этой категории; повторное нажатие, нажатие на другую плитку или клик вне панели закрывают его
- **Ширину панели можно регулировать**: тяните правую границу мышью. Двойной клик по границе возвращает ширину по умолчанию. Выбранная ширина запоминается между запусками
- Плитки не разъезжаются при изменении ширины: колонки фиксированной ширины, новая ширина добавляет плитки в ряд, а не растягивает существующие
- Третий уровень уникален внутри подкатегории: повторный запуск не дублирует статьи

**Значки и цвета категорий**
- **Значок** — 41 цветная иконка (машинка, грузовик, топливо, еда, кофе, здоровье, спорт, одежда, дети, животные, подарки, интернет, деньги и другие). Выбор в «Управление категориями» → нажатие на значок слева от названия
- **Цвет сектора на графике** — палитра из 18 контрастных цветов, выбирается кнопкой рядом со значком. Именно этот цвет используется в кольцевой диаграмме и в разбивке отчёта, поэтому сектора не сливаются
- Между секторами диаграммы рисуется зазор, чтобы соседние цвета не «слипались» даже при похожем тоне
- В легенде диаграммы показывается доля каждой категории в процентах
- Значок и цвет хранятся в БД (`categories.icon`, `categories.color`), старые базы обновляются миграцией без потери данных

**Траты**
- Добавление траты: категория, подкатегория, сумма, дата, комментарий
- Удаление трат, фильтрация по периоду
- Итоговая сумма за выбранный период

**Внесение денег**
- Кнопка «Внесение» — операция поступления денег (отличается от «Указать остаток», который фиксирует снимок текущего состояния)
- **Категория внесения обязательна.** Ошибку нельзя обойти: кнопка неактивна без категории, проверка дублируется в главном процессе (`db:addDeposit`)
- **Справочник категорий внесений** («касса», «зарплата», «выручка»…) — отдельный от категорий трат. Управление: «Управление категориями» → раздел «Категории внесений»
- **Цвет категории внесения** выбирается там же, кнопкой слева от названия. Цвет определяет сектор на графике «Приход по категориям» и сохраняется в тот же файл Excel. Категориям без выбранного цвета палитра подбирает свободный оттенок, поэтому сектора не совпадают
- Новую категорию можно создать прямо в форме внесения, не закрывая окно
- Отдельная вкладка «Внесения» со списком операций и итогом
- Внесения учитываются в отчёте за период, там же — разбивка по категориям внесений

**Перенос старых комментариев в категории (миграция 1.0.8)**
- Все прежние комментарии внесений превратились в категории автоматически при первом запуске
- **Одинаковые комментарии объединяются в одну категорию.** Сравнение идёт без учёта регистра и лишних пробелов: `зарплата`, `Зарплата` и `ЗАРПЛАТА ` станут одной категорией, в качестве названия возьмётся первая встреченная формулировка
- Историческая формулировка сохранена в колонке `deposits.note` — она больше не показывается в интерфейсе, но и не потеряна
- Миграция требует пересоздания таблицы `deposits` (в старой схеме комментарий был `NOT NULL` с `CHECK`) и выполняется в одной транзакции; перед ней автоматически делается резервная копия
- Удаление категории внесения **не удаляет сами внесения** — у них просто пропадает метка, суммы и даты остаются. В отчёте такие внесения попадают в «Без категории»

**Остаток**
- Кнопка «Указать остаток» фиксирует базовую сумму на конкретную дату (сверка с банком)
- **Текущий остаток производный**: последняя отметка + все внесения после неё − все траты после неё. Внесение сразу отражается в остатке
- Если отметок нет, остаток считается от нуля по всем операциям
- Порядок операций в пределах одного дня определяется временем ввода, поэтому внесение, сделанное после отметки в тот же день, учитывается

**Отчёт за период: три вкладки**
- **Общий отчёт** — то, что было: карточки начала/внесений/трат/выхода, движение денег, графики, разбивка расходов по трём уровням и итоги внесений. Списка внесений по датам здесь нет — он целиком переехал на вкладку «Внесения», иначе одни и те же числа показывались бы дважды
- **Траты** — только расходы: сумма за период, количество операций, число категорий, средняя трата; кольцевая диаграмма расходов, динамика по дням только с тратами, разбивка категория → подкатегория → статья
- **Внесения** — только поступления: сумма, операции, категории, среднее; кольцевая диаграмма прихода, динамика по дням только с внесениями, список внесений и блок итогов
- На вкладках видно счётчики операций, а графики и таблицы соответствуют выбранной вкладке, а не всегда показывают всё сразу

**Отчёт за период (макрос)**
- Кнопка «Отчёт» формирует сводку:
  - **начало (база)** периода
  - сумма **внесений**
  - сумма **трат**
  - **на выходе** — деньги после всех внесений и вычетов
  - графики: кольцевая диаграмма расходов по категориям, кольцевая диаграмма **прихода по категориям внесений** и динамика по дням
  - разбивка по трём уровням: категория → подкатегория → статья
  - внесения сгруппированы по категориям внесений
  - **блок «Итоги внесений» в самом низу отчёта**: всего внесено, операций, категорий, среднее, плюс таблица с долями и строкой «Итого»
- Формула: `на выходе = начало (база) + внесения − траты`
- Если отметка «Указать остаток» попадает внутрь периода, она становится базой периода: операции до неё уже учтены в её сумме и повторно не считаются
- Экспорт отчёта в CSV — вместе с данными, на которых построены графики (отдельными секциями «ГРАФИК 1: расходы по категориям», «ГРАФИК 2: приход по категориям» и «ГРАФИК 3: динамика по дням»)
- **Экспорт отчёта в Excel (.xlsx) с нативными графиками.** Графики вставляются как настоящие диаграммы Excel, а не картинки: их можно двигать, перекрашивать и пересчитывать прямо в Excel. В файле три диаграммы (расходы, приход, динамика), макро-итоги и полные списки трат и внесений. Цвета секторов совпадают с цветами в приложении

> Графики в CSV не попадают как картинки: формат CSV текстовый и не умеет хранить изображения. В него выгружаются **данные** графиков, по которым их можно заново построить в Excel или Google Sheets. Готовые диаграммы внутри файла даёт экспорт в XLSX.

**Обновление программы**
- Пункт «Проверить обновление» в меню «Файл». Если новая версия найдена, она качается автоматически с показом прогресса, затем по кнопке программа закрывается, обновляется и запускается заново
- Если сервер обновлений недоступен, программа не зависает: показывается причина и ссылка на страницу релизов. Проверка ограничена 30 секундами
- Канал обновлений — **GitHub Releases** репозитория. Артефакты Actions для этого не подходят: они временные и требуют авторизации, а программе нужен постоянный адрес
- Публикация происходит только при сборке **по тегу** `v*`. Обычные сборки из ветки `main` публикуются лишь как артефакты — иначе установленные копии начали бы предлагать себе сборку из ветки
- **Windows**: автообновление работает, установщик NSIS обновляется тихо, подпись не требуется
- **macOS**: автообновление **отключено**, обновления ставятся вручную. Причина: Squirrel.Mac сверяет «designated requirement» новой сборки с требованием уже установленной программы, а у подписи ad-hoc (`codesign --sign -`) отпечаток меняется при каждой сборке, поэтому требования никогда не совпадут. Пункт меню на macOS сразу объясняет это и даёт ссылку на страницу релизов, вместо того чтобы ходить в сеть

**Тема оформления**
- Переключатель в правой части шапки: солнце включает светлую тему, луна — тёмную
- Выбор сохраняется в `localStorage` и переживает перезапуск
- Тема ставится на `<html>` скриптом в `index.html` **до** отрисовки React. Без этого при запуске на долю секунды мелькала бы тёмная тема поверх светлой
- Обе темы заданы только переменными в начале `styles.css`; светлая переопределяет их в селекторе `[data-theme='light']`. Вся вёрстка уже написана через переменные, поэтому отдельно перекрашивать элементы не приходится
- Акценты в светлой теме намеренно темнее: `#00d4aa` на белом фоне почти не читается, особенно в мелком тексте

**Быстрый ввод**
- Панель поиска над таблицей: комментарий, категория, подкатегория, статья и сумма. Пробел в запросе означает «любые слова в любом порядке», поэтому «куртка женское» находит оба слова
- Фильтр по диапазону сумм рядом с поиском. Пока фильтр включён, рядом показывается, сколько записей он скрыл, а итоги в шапке пересчитываются по найденному — сумма на экране всегда соответствует тому, что видно в таблице
- Если под фильтр ничего не подошло, показывается не «нет трат за период», а «ничего не найдено» с кнопкой сброса: пустой период и пустой результат поиска — разные вещи
- Фильтр применяется к обеим таблицам (траты и внесения): один и тот же запрос работает на обеих вкладках
- Кнопка «Повторить» на каждой строке открывает форму уже заполненной: категория, подкатегория, статья, сумма и комментарий. Дата при этом всегда сегодняшняя — повторяют расход, а не старый чек
- Отмена удаления: после удаления траты или внесения в тосте появляется кнопка «Отменить» (8 секунд вместо обычных 4 — иначе нажать не успевают). Запись возвращается с прежним `id`: иначе `AUTOINCREMENT` продолжал бы счёт от максимума и при следующем добавлении появился бы дубль
- Горячие клавиши: `Ctrl+N` трата, `Ctrl+D` внесение, `Ctrl+F` поиск, `Esc` закрыть окно. Список показан в меню «Файл»
- Фильтрация выполняется в памяти: период уже загружен целиком, а запрос к базе на каждый ввод буквы только тормозил бы

**Регулярные платежи**
- Аренда, связь, подписки и проездной задаются один раз, а программа сама напоминает, когда платить. Настройка — меню «Файл» → «Регулярные платежи» или ссылка «все» в блоке боковой панели
- Форма нового платежа стоит **над** списком и свёрнута: постоянно висящая форма занимала бы пол-окна, когда платежей нет, и отвлекала бы, когда они есть. Разворачивается по кнопке «Новый платёж»
- Значок календаря справа сверху открывает **календарь платежей** по месяцам: у каждого дня с платежом отмечена точка цвета категории, стрелки листают месяцы. Под сеткой — платежи выбранного дня с кнопкой «Оплачено». Кнопка появляется только для наступивших дат: отметить будущий платёж — значит внести его задним числом
- Периоды: ежедневно, еженедельно, ежемесячно, ежеквартально, ежегодно
- В боковой панели появляется блок «Пора оплатить» с наступившими платежами. Просроченные подсвечиваются красным, их количество вынесено счётчиком в заголовок
- Кнопка «Оплачено» одним кликом создаёт трату и сдвигает платёж на следующий период
- Внизу блока и вверху окна показывается сумма постоянных расходов в месяц. Дневные и недельные платежи пересчитываются в месяц, поэтому цифра сопоставима с месячной арендой
- Платёж можно выключить, не удаляя: история созданных им трат сохраняется, а сам платёж перестаёт напоминать
- Удаление платежа не трогает уже созданные траты — об этом прямо сказано в подтверждении

Технические решения, из-за которых это работает:

- Хранится **дата следующего платежа**, а не «день месяца». Пока она в прошлом, платёж считается просроченным, а отметка «оплачено» двигает дату вперёд. Пропущенные месяцы не копятся: одна отметка погашает весь долг (`advanceUntilFuture`)
- Дата сдвигается в JS, а не в SQL: SQLite не умеет прибавлять месяцы. Наивное прибавление через `setMonth` переполняет месяц — 31 января превратился бы в 3 марта. День обрезается по длине целевого месяца, поэтому аренда за 31-е возвращается на 28-е в феврале и на 29-е в високосном году. Проверено отдельно на девяти граничных случаях
- Трата и сдвиг даты идут **в одной транзакции**: при сбое между ними получилось бы либо потерянная трата, либо платёж, который никогда не спишется
- Тратой становится дата наступления, а не сегодня. Если аренда должна была прийти 1-го, а отмечена 3-го, в статистике она лежит в том месяце, который оплачивали
- Даты разбираются вручную, без `new Date('2026-01-31')`: такая строка разбирается как UTC и в местном поясе съезжает на соседний день
- Календарь считает даты на сервере **той же** функцией сдвига, что и кнопка «оплачено». Иначе два экрана об одном платеже могли бы разойтись: календарь показал бы 28-е, а трата создалась бы с другой датой

**Скорость запуска**
- Приложение упаковано в `app.asar` размером около 2.6 МБ. `react`, `react-dom` и `lucide-react` помещены в `devDependencies`: Vite собирает их в `dist/renderer`, и в рантайме главному процессу они не нужны, а electron-builder иначе складывает их в пакет — asar раздувался до 26 МБ, и Electron перебирал лишние файлы при каждом старте
- В зависимостях осталось только то, что реально исполняется: `better-sqlite3` и `jszip`
- `jszip` подключается **лениво** — только в момент экспорта в Excel. Его разбор занимает около 45 мс, и раньше эта плата взималась при каждом запуске
- Замер на этой машине: инициализация БД ~110 мс, создание окна ~45 мс, отрисовка интерфейса ~170 мс, данные на месте через ~6 мс после загрузки

**Периоды**
- Быстрые пресеты: День, Неделя, Месяц, Квартал, Год
- Произвольный выбор дат вручную

## Разработка

Требуется Node.js 20 (LTS).

```bash
npm install
npm run dev                # запуск в режиме разработки
npm run typecheck          # проверка типов
npm run build              # сборка renderer + main
npm run build:template-db  # генерация resources/template/expenses.db
npm run build:win          # сборка установщика .exe для Windows (включая базу)
npm run build:portable     # portable-версия .exe для Windows (без установки)
npm run build:mac          # сборка .dmg для macOS (arm64) — только на macOS
```

### Портирование на iOS / Android

Логика вынесена в слои, которые переиспользуются:
- `src/renderer/types.ts` — модели данных
- `src/renderer/lib/format.ts` — форматирование и периоды (без зависимостей от DOM/Node)
- `src/main/schema.ts` — схема БД и дефолтные категории
- `src/main/main.ts` — SQL-запросы остатка и отчёта (переносятся в мобильную БД как есть)
- `src/renderer/components/` — React-компоненты

Для мобильной версии заменяется только транспортный слой (`window.electronAPI` → HTTP/React Native SQLite), компоненты и логика отчётов остаются прежними.

### Как база попадает в установщик

1. `npm run build:template-db` генерирует `resources/template/expenses.db` — пустую БД со схемой и дефолтными категориями. Скрипт запускается под Electron, т.к. `better-sqlite3` собран под ABI Electron.
2. Схема и дефолтные категории берутся из `src/main/schema.ts` — это единый источник истины для рантайма и генератора шаблона.
3. electron-builder кладёт базу в `resources/template/` внутри приложения (`extraResources`).
4. При первом запуске `main.ts` копирует шаблон в `%APPDATA%`, если БД ещё не существует.
5. `applySchema()` вызывается при каждом старте и идемпотентна: обновляет структуру, но не трогает пользовательские данные.
